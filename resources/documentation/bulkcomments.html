Bulk Comments for Jira

Bulk-comment on multiple Jira issues – up to 25 at once, a different comment and status on each.

v4.6.0 — Latest Runs on Atlassian Atlassian Forge Jira Cloud

Overview

Bulk Comments for Jira is an Atlassian Forge app installed directly inside Jira Cloud. Pick up to 25 issues, then give each one its own comment, its own attachments and its own status change — all on one page, in three steps.

The Full Guide below walks through each step with screenshots.

Runs on Atlassian: the app carries Atlassian’s Runs on Atlassian badge, granted only to apps that store and process data entirely on Atlassian infrastructure with no external egress. Nothing you write, attach or select leaves your Jira instance, and there is no DataPingo server in the path to be breached. See Specs & security for the full posture.

No context switching: Everything happens inside Jira. There's no external server in the data path — comments and media move straight to Jira through Atlassian's own infrastructure.

Full Guide

Where to open it from

Two places, doing deliberately different jobs:

  • The left sidebar → Bulk Comments for Jira — the full app, starting at the Select step with nothing selected.
  • An issue’s ••• actions menu → Bulk Comments — opens the full app at the Select step with that issue already selected, so you carry on picking the rest. Everything the app can do is there.

Step 1 — Choosing issues

Every issue you can see in Jira is here by default. The controls along the top narrow that down; the tray along the bottom holds what you have picked. Nothing is committed at this step — you can come back and change the selection at any point before you send.

  • Search — search by keyword or issue key, or paste a key straight in. Two modes sit beside the field: Basic for plain search, and JQL when you want a precise query. Sorting and filtering are applied inside the query itself, so they reorder the whole result set rather than just the rows already on screen.
  • Project — defaults to All projects. Open it to scope the list to one project, and if you have a lot of them, the dropdown carries its own Search projects field so you can type rather than scroll.

    Every row carries a small mark before its summary, so a mixed list stays readable at a glance:

    • Lightning bolt — Jira Service Management
    • Person — Customer Service Management
    • Lightbulb — Jira Product Discovery
    • —No mark — Jira Software and Jira Work Management, the ordinary case

    The mark matters because it tells you which issues will offer a Reply to customer choice on the next step. Only the first two ever do.

  • Status — tick the statuses you want to see. The names are read from the projects in your results, so you get your own workflow’s wording — “In Review”, “Awaiting QA”, “Blocked” — rather than generic categories. Done work is hidden by default; one tick brings it back. The list carries three shortcuts:
    • Select all / Deselect all — one toggle at the top of the list, which flips depending on where you are
    • Only — every status carries one, with a count beside it. It jumps straight to that single status instead of making you untick the other nine
    • Reset to open issues — back to the default in one press

    The header then reads how many you have hidden, so a filtered list never looks like an empty one.

  • Assigned to me — off by default, so you see everyone’s issues. One click narrows the list to only the issues assigned to you; click again to see everyone’s.
  • Sort — three fields, each taking its natural direction first:
    • Updated — most recently changed first
    • Issue key — by key, so a project’s issues run in order
    • Summary — alphabetical, A–Z

    The arrow beside the field flips between ascending and descending.

  • Select all visible — ticks every issue currently on screen, up to the 25 ceiling. Once everything visible is picked it flips to Deselect all and clears them, so it is its own undo. Pair it with the project filter and you can take a whole project in two clicks.

The tray along the bottom lists every issue you have picked, no matter which search you found it in — so a selection built from three different queries is still visible in one place, with the counter reading n / 25 selected. Press the × on any chip to drop that issue without going back to hunt for it.

This is always the first step, whatever you write once you get to the issues you picked.

Step 2 — Writing a comment

Every issue you picked is its own card, always — its own comment, its own attachments, its own status control. There is nothing to choose before you start; you land on the list already able to write.

What is on a card. Reading the header from left to right:

  • Issue key and Details › — one control, not two. Pressing either the key or the issue title opens the details panel on the right; it does not open Jira. To reach the issue itself, use the key chip inside that panel — it carries an ↗ and opens a new browser tab.
  • Use this comment for all — appears once there is something to copy, and only when more than one issue is selected.
  • Internal / Reply to customer — service desks only. These appear on Jira Service Management and Customer Service Management issues and nowhere else. Those same cards also carry Also reply to the customer at the foot of the editor, so one request can hold an internal note and a customer reply.
  • Status — the issue’s current status as a dropdown. One click queues a move, offering only the transitions that issue’s own workflow allows.
  • Ready — a green badge once the card has something to send.
  • × — drops that issue from the batch.

Beneath the header, at a glance, is the issue’s summary, who it is assigned to — or Unassigned — and when it was last commented on. Enough to know what you are writing about without opening anything.

Need the full picture on one before you write? Every card carries a Details › control beside its key — press it, or the issue title, and a separate panel opens on the right with that issue’s description, its details, its attachments and its comment history. It is read-only and entirely apart from the card you are writing in: close it, or never open it, and nothing about what you have already written changes. Only one panel is open at a time.

Opening the issue in Jira. On a card, the key is part of the Details control — it opens the panel, not Jira. To jump to the issue itself, use the key chip in the panel’s own header: it carries an ↗ and opens the issue in a new browser tab, leaving everything you have written untouched. Subtasks, linked work items and individual comments listed in the panel open the same way.

That panel shows the 25 most recent comments on the issue, in full. An issue with more than that reads All comments · 25+ and adds a note — “Showing the 25 most recent. Open in Jira for the full history.” — under the list, so you always know when you are looking at everything versus just the recent slice.

Images, video and files in that history play or preview right there in the panel — a video plays inline with a thumbnail before you click, and images open in a full-size viewer. Nothing here sends you out to Jira to see what a past comment actually attached.

Attachments on the comment you are writing work the same way, right there in the card, up to 150 MB per file — see The comment editor.

Who is allowed to read it — service desks

On a Jira Service Management or Customer Service Management request, a comment is one of two different things. An Internal note is seen by agents only. A Reply to customer reaches the customer and emails them. They are never the same sentence, and on a batch of twenty-five that difference is the whole job.

So every service-desk card carries the choice in its header, next to its status. It is per request, not per send — one run can answer three customers and leave two notes for the team. Issues from Jira Software, Jira Work Management and Jira Product Discovery have no such distinction and show no control; their comments are simply comments.

A reply to a customer cannot be taken back. The email is gone the moment it posts. This is why the app no longer offers an undo, and why the confirmation before a send names exactly how many customers that send will reach — that number is the last thing you see before it goes.

Both at once — the reply and the note behind it

Answering a customer usually leaves something to record that the customer should not read: what actually caused it, what you tried, what to watch next time. One request can carry both.

Also reply to the customer sits at the foot of a service-desk card. Press it and a second box opens beneath the first, labelled so you can never mix them up: Internal note — agents only · posted first, and Reply to customer — emailed to the customer · posted second. Write them separately; they post together, in that order, as one issue’s work.

The second box is always the opposite audience to the first, so a pair can never drift into two comments that both go to the customer. Close it with the × on its header and the card goes back to a single comment.

This is why twenty-five issues can produce fifty comments. The cap the app enforces is on issues, not comments — see Limits.

Writing one comment once — Use this comment for all

Some batches genuinely do want the same words everywhere: an incident is resolved, a release shipped. Write it in any one card, then use Use this comment for all to copy it into every other card in the batch.

It is a copy, not a link. Every card stays independently editable afterwards, so the normal pattern is to paste the shared version everywhere and then change the two that need saying differently. On a service desk the copy respects each card’s own audience rather than overriding it.

Ready, or skipped

An issue with a comment written on it carries a Ready badge; an issue with only a status change queued and no comment reads Status only. An issue with neither carries no badge at all — nothing has happened to it yet, so there is nothing to announce.

An untouched issue is skipped when you send — nothing is posted to it and nothing happens to it. The footer counts everything, so “2 ready · 3 skipped” tells you exactly what is about to go out before you press anything.

Changing an issue’s status

Every card carries its current status as a dropdown in its header — TO DO, IN REVIEW, whatever the issue is on right now. Click it and you get that issue’s own workflow transitions, so you only ever see moves Jira would accept. Pick one and the button switches to show where the issue is heading; a small × clears it again. Each issue moves independently: one to In Review, the next to Done, and the rest left alone.

Choosing a transition that lands on the status the issue is already in is marked as such and quietly skipped at send time, so a redundant move never counts as work that happened.

A status change can travel on its own. An issue with a new status and no comment still counts as ready and is included in the send — it is not treated as a blank row and skipped.

Starting over — Clear all

Clear all sits above the issue list and wipes the work rather than the selection: every comment you have written and every status change you have queued. It asks first — the button changes to Clear comments & statuses? and needs a second click, so a stray press costs nothing.

What it deliberately does not do is send you back to the Select step. The issues you picked stay picked, so this is the fast way to rewrite a batch from scratch without hunting down the same 25 issues a second time. Nothing has been posted to Jira at this point, so there is nothing to undo — clearing only affects what is on screen.

Attachments work the same way here as anywhere else in the editor — see The comment editor for how files are attached, sized and uploaded.

Step 3 — Sending and delivery

The Send step tracks every issue individually and posts them in parallel, so a batch of 25 goes out together rather than one after another. Three counters — Updated, Sending, Failed — update live above a row for every issue, and each row links straight to the comment on its issue. When the run finishes the heading changes to Comments posted and tells you how long it took.

Each row says what actually happened to that issue: Updated when a comment posted, Status changed when the issue only moved, No change needed when a queued move turned out to be redundant, or Failed with the reason Jira gave. While the run is in flight a row reads Queued… and then Posting….

Anything that fails gets a Retry n failed button that re-runs only those issues, leaving the ones that already landed untouched.

Most sends finish with nothing in the Failed column. When something does fail it is usually a permission change, or an issue that was moved or deleted while the batch was running — and the row carries the reason Jira returned.

If a retry keeps failing, tell us. Two ways to reach us:

  • Raise a support request — tracked, and the fastest way to get an answer
  • support@datapingo.com — if you would rather email

Either way, send the issue keys and the reason shown against each failed row. Those two things are usually enough to say what happened rather than leaving you to work it out.

Every row opens its issue: click the issue key or the ↗ on the right and it opens in a new tab — scroll to the bottom of the issue to see the comment or the change that landed.

Every row says who saw it. On a service desk a row carries an INTERNAL badge, and adds + SENT TO CUSTOMER when that request also carried a reply. So the record of who was emailed is on the results screen itself, not something you reconstruct afterwards.

There is no undo. It was removed in 4.6.0. An undo could never honestly cover a service desk — by the time you press it the customer’s email has already been sent — and an undo that works on four products out of five is worse than none, because it teaches you to rely on it. The confirmation before sending replaces it: it names the issue count, the storage total, and how many customers the send will reach.

To remove a comment after the fact, delete it on the issue in Jira. Deleting a customer-facing reply does not unsend the email.

Heads-up before a big send. A confirmation appears first if any of three things is true: you are posting to 10 or more issues, the comment @mentions someone (every issue notifies them separately), or the files you have attached come to 50 MB or more. The size one catches sends that are small in issue count but heavy in bytes — two issues and one long video will ask before it starts, and tells you to keep the tab open until it finishes.

It shows the storage arithmetic first. A file lands once on every issue you send to, so the total written into Jira is the file size multiplied by the issue count — 150 MB across 9 issues is 1350 MB. The confirmation does that multiplication for you and names the figure before anything is posted, so a send never surprises your instance.

2 GB is the ceiling for one send. That is the total across every issue, added together rather than multiplied out per issue — one issue at 700 MB, another at 1 GB and a third at 300 MB comes to 2 GB and still goes. Past that the send stops before it starts and asks you to revise the comments or work in smaller batches, rather than failing halfway through and leaving some issues done and some not. The per-file limit of 150 MB applies separately and is checked the moment you attach.

Light and dark

There is no theme setting to find, because the app does not have a theme of its own. It renders in whichever colour scheme Jira hands it, so it is light when your Jira is light and dark when your Jira is dark — including the comment editor, the status lozenges and the readiness badges, which are tinted for each scheme rather than inverted.

The comment editor

Everything you write is posted as native Jira formatting, so a comment sent from here is indistinguishable from one typed into Jira itself — same headings, same tables, same code blocks, same file cards. The toolbar and the keyboard shortcuts deliberately mirror Jira's own editor, so there is nothing new to learn.

Shortcuts below are written in Mac notation. On Windows and Linux read ⌘ as Ctrl, ⇧ as Shift and ⌥ as Alt. The app detects your machine and shows the right one in every tooltip.

Tables

The table button opens a size grid — drag across it to choose how many rows and columns you want. Once the cursor is inside a table, a second row of controls appears with everything you need to reshape it:

  • Header row and Header col — toggle either independently, so a table can have a header row, a header column, both, or neither.
  • Add columns before or after the current one, and add rows above or below.
  • Delete table to remove the whole thing in one click.

Code blocks

A code block keeps your indentation and monospacing intact, and carries a language selector with 42 languages — Bash, C, C++, C#, CSS, Dart, Go, GraphQL, Groovy, Haskell, HTML, Java, JavaScript, JSON, Kotlin, Python, Ruby, Rust, SQL, TypeScript, YAML and more, plus (None) for plain text. The language travels with the comment, so Jira highlights it correctly on every issue you post to.

Mentions, links and emoji

  • @mentions — type @ and search your Jira users. Mentioned people are notified on every issue the comment lands on, which is why a send containing a mention always asks you to confirm first.
  • Smart links — paste a Jira or Confluence URL and it converts into a live link card showing the item's title, status, priority and assignee, fetched fresh rather than frozen at paste time.
  • Emoji — browse from the toolbar or type /emoji.

Attachments

Attach files three ways: drag them into the editor, paste a screenshot straight from the clipboard, or use the toolbar button. Dropping a file places it where your pointer is, not where the cursor happened to be.

  • Up to 150 MB per file, with no limit on how many files one comment can carry. If your Jira site sets a lower attachment limit, that one wins — the app reads the site's real limit and checks against it the moment you attach, so an oversized file is refused immediately rather than after you have written the comment.
  • Uploading starts on attach, not on Send. The file moves while you are still typing, so the send itself is usually near-instant. Nothing is visible on any issue until you actually send, and anything you attach and then delete is discarded.
  • Images and video preview inline, align left, centre or right, and resize by dragging the edge — the same handles Jira gives you. PDFs and other documents post as file cards.
  • Large files upload through an async queue in the background, so a long video posting to 25 issues never stalls or times out the batch.
  • A whole send is capped at 2 GB, counted across every issue in the batch rather than per issue. That is a separate ceiling from the 150 MB per file, so a batch can go over the total while every individual file sits well inside its own limit — four 120 MB files going to 5 issues is 2400 MB and will not send. Nothing is posted when it trips; split the issues across two sends and the total resets. See Files and uploads in Troubleshooting.

Limits

Three numbers govern how much one send can carry. They are independent of each other, so a batch can sit comfortably inside two of them and still be refused by the third.

LimitValueCounted how
Issues per send25Per send. The tray on the Select step stops you selecting a 26th.
Comments per send5025 issues, and a service-desk request can carry two — an internal note and a reply to the customer. The issue ceiling is what is capped; the comment count follows from it.
Size per file150 MBPer file — not per comment. One comment can carry as many files as you like, each up to 150 MB.
Total per send2 GBAdded together across every issue in the batch, after multiplying each file by the issues it lands on.

Why the total is bigger than it looks

Attachments in Jira belong to an issue, not to a comment, so a file you send to 9 issues is written 9 times. The figure that counts against the 2 GB ceiling is therefore file size × issue count, not the size of what you attached.

A worked example: four 120 MB videos is 480 MB in the editor, and every file is well inside the 150 MB per-file limit. Send that to 5 issues and Jira receives 2400 MB — over the ceiling, and the send is refused. Send it to 4 issues instead and it is 1920 MB, which goes.

You see the arithmetic before anything posts. The confirmation on a large send does the multiplication for you and names the figure — “this send adds 1350 MB to Jira” — so the storage cost is on screen while you can still change your mind.

Nothing is posted when a limit trips. A send over 2 GB stops before it starts rather than failing partway through, so you are never left with some issues commented and some not. Split the issues across two sends and the total resets — the ceiling is per send, not per day or per batch of work. An oversized single file is refused at the moment you attach it, before you have written anything.

If your Jira site sets a lower attachment limit than 150 MB, that one wins — the app reads your site’s real limit and checks against it. Jira’s own instance-wide storage quota is separate again and is not something the app can see; if you hit that, see Files and uploads in Troubleshooting.

Installation

Installing takes about a minute and needs a Jira Cloud site admin, since apps are installed site-wide.

  1. Open Bulk Comments for Jira on the Atlassian Marketplace, or search for it from Apps → Explore more apps inside Jira.
  2. Click Try it free and choose your Jira Cloud site.
  3. Accept the permissions it asks for: read and write Jira work items, read Jira user profiles, and app storage. Nothing else is requested — see Permissions Required for what each one does.
  4. Open it from Apps in the left sidebar, or from any issue's ••• actions menu.

Free for teams of 10 or fewer. Above that, paid tiers are billed through the Atlassian Marketplace on your existing Atlassian invoice — there is no separate DataPingo account to create and no card to enter with us.

Removing the app is just as clean. Uninstalling from Apps → Manage apps deletes everything it stored, and comments already posted stay on their issues as ordinary Jira comments.
